# Доказательный RAG по ТФКП

ФИО: **указать перед сдачей**. Группа: **указать перед сдачей**.

Реализация задания `homework_01_rag.md`. По уточнению пользователя корпус и открытый набор создаются кодом из приложенных PDF и `tfkp_15_qa.md`. Исходного `runtime.json`, официального корпуса, dev JSONL и эталонного baseline среди вложений не было. `runtime.json` здесь собственный, с `official=false`; его нельзя выдавать за настройки организатора. Генеративные эксперименты пока не выполнены: endpoint не задан, доступ к Hugging Face в среде заблокирован (403). Числа качества не придуманы.

## Окружение и данные

Проверено на Linux x86_64, Python 3.11.11. PDF извлекают PyMuPDF 1.26.6 и fonttools 4.61.1; они устанавливаются из `requirements.txt`, отдельный Poppler для подготовки данных больше не нужен. Все Python-зависимости, включая транзитивные, точно закреплены; PyTorch берётся из официального CPU wheel index. Lock рассчитан на Linux x86_64/Python 3.11.

```bash
python3.11 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python prepare_data.py --pdf /path/to/textbook.pdf --qa /path/to/tfkp_15_qa.md --output ./data
python -m pytest
```

`prepare_data.py` обрабатывает **весь PDF**, без ограничения §§ 2–6. Создаёт `corpus.jsonl`, `dev_questions.jsonl`, `dev_gold.jsonl`, 8 `own_questions.jsonl`/`own_gold.jsonl` и манифест хешей. Списки эталонов используются только оценкой. Повторная генерация требует пустой выходной папки. Авторские вопросы также сохранены в корне решения, привязаны к приложенному PDF SHA-256.

Исходный блок — непустая страница PDF, ID `pdf_<sha256 PDF[:12]>_p<страница:04d>`. Это собственные стабильные ID, а не восстановленные ID отсутствующего официального корпуса. Страница считается с 1. Кириллица восстанавливается по шрифтовой кодировке. `rag/pdf_math.py` читает математические глифы из встроенных TeX-шрифтов и геометрию PDF: надчёркивания, дробные черты, степени/индексы, корни, растянутые скобки и модули. Математические фрагменты сохраняются в TeX-представлении с Unicode-символами. Никаких LLM, OCR, готовых формул по номерам страниц, чтения gold внутри извлекателя или ручной правки корпуса нет.

Для обновления ранее созданных данных используйте новые выходные папки:

```bash
python -m pip install -r requirements.txt
python prepare_data.py --pdf ./private_data/textbook.pdf --qa ./private_data/tfkp_15_qa.md \
  --output ./data/v2 --audit-dir ./runs/audit_v2
TFKP_TEST_PDF=./private_data/textbook.pdf python -m pytest
python build_index.py --corpus ./data/v2/corpus.jsonl --output ./index_v2_bm25 --config config.json --lexical-only
```

`--audit-dir` сохраняет тексты **всех** страниц и `extraction_audit.json`. `data_manifest.json` содержит `page_reports` и `needs_manual_review_pages`: неразобранные линии, неизвестные глифы, изображения и векторные рисунки требуют проверки. На проверенном PDF 147 страниц обрабатываются без неизвестных глифов и управляющих символов; регрессии проверяют ключевые формулы на страницах 11, 12, 13, 20, 21, 31, 33, 34, 36, 37, 38. Геометрические эвристики не гарантируют смысловую эквивалентность всех формул произвольного PDF. Сложные диаграммы автоматически не интерпретируются. Аудит содержит текст корпуса: храните его в `runs/` и не публикуйте.

Для новых данных используйте вопросы и gold из `data/v2/` и пересобранный индекс. У неизменённого PDF сохраняются прежние `block_id`; позиции символов и хеш корпуса меняются, поэтому старые индексы не подходят. `local_validation.json` описывает исходный прогон; `extraction_validation.json` — проверку исправленного извлечения. При обычном `python -m pytest` проверка частного учебника пропускается; переменная `TFKP_TEST_PDF` включает её без добавления PDF в репозиторий.

Если организатор предоставит исходный `corpus.jsonl`, его можно подать прямо в `build_index.py`: система сохранит его `block_id`. Для него нужны соответствующие официальные gold-файлы; текущие gold привязаны к самостоятельно созданным страничным блокам.

## Модели и runtime

Разрешённый генератор — только `Qwen/Qwen3.5-4B`, через API. Локально используются только его tokenizer/chat template, без генеративных весов. Dense-модель — `intfloat/multilingual-e5-small`, Sentence Transformers на CPU, без дообучения. Код проверяет фактическое число параметров: не более 1 млрд. Нет reranker и других генераторов.

Перед прогоном в среде с разрешённым доступом к хранилищу моделей:

```bash
python prepare_models.py --config config.json --resolve-revisions
```

Этот **отдельный подготовительный шаг** однократно разрешает HEAD в точный commit SHA, записывает его в `config.json`/`runtime.json`, скачивает разрешённые модельные артефакты и создаёт `models.lock.json` с SHA-256 каждого файла. При дальнейших запусках HEAD не используется. После подготовки сохраните изменённые конфигурации и небольшой lock в репозитории; веса туда не добавляйте. Готовый `models/` можно перенести из разрешённой среды вместе с lock. Не обходите сетевую политику.

Согласуйте с обслуживающим endpoint `llm.revision`, `llm.quantization`, thinking и sampling. Затем установите `server_revision_verified=true` в `runtime.json`. Это декларация проверенной конфигурации сервера, не автоматическая проверка удалённых весов. Пока ревизия/квантизация не заданы и не подтверждены, `predict.py` завершится до вызовов API. Собственные начальные параметры: temperature=0, top_p=1, max_tokens=1024, thinking=false. После получения официального runtime они должны быть заменены по нему, через явно проверяемую схему `rag/config.py`, и оставаться одинаковыми для всех пяти режимов.

## Индексация и ответы

```bash
python build_index.py --corpus ./data/corpus.jsonl --output ./index --config config.json

# Экспортируйте LLM_BASE_URL, LLM_MODEL, LLM_API_KEY и SUBMISSION_ID
# из предоставленного доступа. Не вставляйте секреты в код/логи/репозиторий.
python predict.py --index ./index --questions ./data/dev_questions.jsonl \
  --output ./runs/final/answers.jsonl --trace ./runs/final/trace.jsonl --config config.json
```

Все файлы индекса находятся в `--output`. Пути моделей/runtime разрешаются относительно файла конфигурации, CLI-пути — относительно текущей папки. Можно запускать скрипты абсолютным путём из любой папки. Индекс и выходные файлы не перезаписываются. При ответах Hugging Face offline, модели `local_files_only`, redirects и скрытые HTTP retries отключены; единственная сеть — POST в `${LLM_BASE_URL}/chat/completions`. API alias берётся из `LLM_MODEL`, чтобы проверяющий мог подставить свой endpoint.

Без весов доступна диагностика, **не финальная система**:

```bash
python build_index.py --corpus ./data/corpus.jsonl --output ./index_bm25 --config config.json --lexical-only
python retrieval_diagnostics.py --index ./index_bm25 --questions ./data/dev_questions.jsonl \
  --gold ./data/dev_gold.jsonl --config config.json --output ./runs/retrieval.json
```

После подготовки моделей и сборки полного индекса можно сравнить поиск без API Qwen:

```bash
for profile in simple no_dense no_neighbors final; do
  python retrieval_diagnostics.py --index ./index --questions ./data/dev_questions.jsonl \
    --gold ./data/dev_gold.jsonl --config config.json --profile "$profile" \
    --output "./runs/retrieval_${profile}.json"
done
```

Все режимы сравниваются на одном полном индексе. `simple` — BM25; `no_dense` — BM25 с соседями; `no_neighbors` — hybrid; `final` — hybrid с соседями. В `candidate_context_fragments` сохраняются точные тексты и диапазоны выбранных окон для сверки с PDF. Эти диагностические файлы содержат текст корпуса: храните их в игнорируемой папке `runs/`. Метрика по страницам предварительная, до упаковки по Qwen-tokenizer; она не проверяет сохранность формул и не измеряет правильность ответа.

## Архитектура и бюджет

1. Страница делится на окна до 1000 символов, с перекрытием до 160. Для dense окна дополнительно уменьшаются по реальному tokenizer до 512 токенов вместе с E5-префиксом. Каждый фрагмент хранит исходный `block_id` и точный диапазон символов.
2. BM25 со стеммингом русского текста и cosine/IP-поиск нормализованных E5-векторов в FAISS `IndexFlatIP`. Запрос включает вопрос и тексты вариантов, без ID вопроса, эталонов и категорий. Длинные dense-запросы разбиваются; скрытого усечения вопроса нет.
3. RRF: `score(d)=Σ 1/(60+rank(d))`. 32 кандидата, разнообразие исходных страниц, до 8 фрагментов, соседние окна той же секции. Контекст пакуется по токенам реального Qwen chat template; цитируются исходные страницы, не номера окон.
4. Один вызов Qwen. Pydantic проверяет JSON, фактические ID вариантов, ≤4 уникальных ссылок только на показанные блоки, согласованный отказ и rationale ≤1200 символов. В финальных режимах возможна одна повторная попытка **только** после ошибки JSON/ID/ссылок и при наличии бюджета. Нового поиска/агентного цикла нет; решение о повторе логируется.

Нельзя доказать семантическую опору ответа одним Pydantic: он проверяет структуру и происхождение ссылок. Ошибки математики/достаточности требуют оценки и проверки обоснований.

Перед каждым запросом резервируется неизменный `max_tokens` из runtime и вход с запасом 192+2%. Лимиты: ≤4 вызовов, ≤16384 входных и ≤4096 выходных токенов на вопрос; вход+допустимый выход запроса ≤8192. Реальные токены берутся только из `usage`, thinking уже входит в `completion_tokens`. Нет автоматических повторов при сетевых ошибках. В каждом POST есть `X-Question-ID` и `X-Submission-ID`.

Отсутствующий `usage` даёт `null` в диагностическом trace, `valid=false` и код выхода 2: такой прогон **не является корректной сдачей**. Технический сбой не засчитывается за содержательный отказ. Положительный лимитный контроль требует полного серверного usage и проверяемого журнала endpoint. Если сервер считает chat template иначе запаса, вопрос останавливается; до большого прогона нужен smoke-тест реального endpoint. Ключи, полные ответы/внутренние рассуждения модели и тела API-ошибок в trace не пишутся.

CPU ограничен 2 потоками, собственный RAM-лимит 4096 MiB: Linux RLIMIT_AS и RSS-monitor. Ограничение адресного пространства консервативно и может сработать раньше лимита физической RAM. Веса, warmup и загрузка индекса отделены от latency вопроса.

## Эксперименты и сдача

Режимы `--profile`: `no_context`, `simple` (один BM25-поиск/один вызов), `final` (hybrid+соседи), `no_dense`, `no_neighbors`. Последние два отключают по одному компоненту финального режима. Sampling и вопросы одинаковы. Closed-book baseline имеет исследовательский формат с пустыми citations даже при выборе вариантов; это **не** формат финальной сдачи и его Q не оценивается.

```bash
python run_experiments.py --index ./index --questions ./data/dev_questions.jsonl \
  --gold ./data/dev_gold.jsonl --corpus ./data/corpus.jsonl --config config.json \
  --output ./runs/experiments --export-submission .
```

Только после пяти успешных реальных прогонов экспортируются `dev_answers.jsonl`, `dev_trace.jsonl`, числовой `experiments.csv`. До этого в CSV пустые ячейки, статус — `experiments.status.json`. `evaluate.py` реализует точное множество вариантов, максимальный citation F1, макро-Q по четырём категориям и стоимость. Официального `C_ref` нет: измеренная стоимость собственного simple baseline не выдаётся за официальную.

`report.md` и `local_validation.json` содержат реальные локальные проверки. Заполните ФИО/группу и дополните отчёт результатами/тремя ошибками **ответов** после доступа к Qwen; сейчас разобраны три наблюдаемые ошибки поиска.


Отдельный архив локальных данных не предназначен для GitHub. Публичный репозиторий исходников: https://github.com/AlinaBakarova/RAG_po_tfkp. Перед сдачей пересоберите полный индекс, выполните пять прогонов, проверьте метрики/лимиты/обоснования и добавьте только предусмотренные небольшие результаты.
